# Архитектура и подход

## Назначение

Агент проверяет исходный код, конфигурацию, зависимости, CI/CD и документацию всего Git-проекта на соответствие восьми требованиям ИБ хакатона. Для анализа используется официальный DeepSeek API; модель выбирается через `DEEPSEEK_MODEL`. Результаты включают доказательства, рекомендации, статусы всех требований и решение для пайплайна.

## Конвейер

1. **Снимок проекта.** Проверяется чистота checkout, фиксируются HEAD и SHA-256 каждого отслеживаемого файла. Файлы читаются без исполнения. Выходные артефакты находятся за пределами объекта проверки. Повторная инвентаризация после анализа обнаруживает изменения снимка.
2. **Полное индексирование.** Обрабатываются UTF-8-тексты и DOCX, включая таблицы. Для Python извлекаются определения, декораторы, импорты и URL-маршруты. Явные бинарные ресурсы и потенциальные секретные файлы получают записанную причину исключения. Неизвестные форматы вызывают ошибку.
3. **Map.** Все извлечённые тексты, включая библиотечные компоненты, делятся на последовательные фрагменты. Каждый фрагмент передаётся DeepSeek с каталогом требований. Модель возвращает наблюдения, включая защитные механизмы, вероятные дефекты и ссылки на исходники. Это ещё не окончательные находки.
4. **Review.** По каждому ИБ-требованию собираются все относящиеся к нему наблюдения, общая инвентаризация, сведения о маршрутах и оригинальные фрагменты. Модель может до четырёх раз запросить дополнительные диапазоны исходников; число раундов и дополнительных разборов ограничено. Превышение бюджета контекста не приводит к тихому обрезанию.
5. **Verify.** Предложенные нарушения проходят отдельный запрос DeepSeek с инструкцией искать опровергающие обстоятельства: внешний декоратор, middleware, неподключённый маршрут, допустимый внутренний HTTP и другие исключения. Существование файлов и диапазонов независимо проверяется программно. Фрагменты в итоговом отчёте берутся из снимка, а не генерируются моделью.
6. **Report and gate.** Структуры проверяются JSON Schema, одинаковые идентификаторы находок удаляются. JSON является источником Markdown. Код 1 зависит только от подтверждённых нарушений ИБ-01…08; дополнительные дефекты приводятся отдельно. Незавершённость означает код 2.

## Полнота при ограничении контекста

Агент не использует git diff как область проверки. Инвентаризация содержит все отслеживаемые пути. Каждый поддерживаемый текст покрывается фрагментами, включая длинные строки; число обработанных фрагментов сохраняется в отчёте. Сводки map по одному требованию не обрезаются: если они не помещаются, оценка считается незавершённой. Оригинальный контекст подбирается в пределах бюджета и доступен по запросу диапазонов.

Так обеспечивается учёт всех файлов и явное выявление неполного выполнения. Семантическая полнота выводов LLM не является математически доказанной: модель может пропустить важный факт. Для оценки качества требуются эталонные тесты и реальные прогоны через API.

После интеграционного запуска добавлены: повторный запрос при некорректном JSON или ссылках на строки, деление фрагмента при обрезанном ответе, включение полных небольших общих компонентов в итоговый контекст и суточный кэш map-наблюдений по хешу текста/модели/инструкций/схемы. Итоговые review/verify всегда выполняются заново. Проверенные нарушения доказывают fail требования даже при отклонении другого кандидата; если все кандидаты неподтверждены, сохраняется inconclusive, а не pass.

## Ресурсы и устойчивость

По умолчанию одновременно выполняются два map-запроса, остальные этапы последовательны. Число повторов ограничено, сетевые ошибки и HTTP 429/5xx обрабатываются отдельно от некорректного JSON. Прогресс сохраняется атомарными контрольными точками. Родительский процесс ограничивает весь запуск по времени, включая зависшие соединения. Фактические токены берутся из поля usage API; длительность измеряется, а стоимость не выдумывается без актуального тарифа.

## Безопасность и ограничения

Ключ берётся из окружения или внешнего `.env`, не включается в аргументы процесса и не передаётся в контекст. Репозиторий считается недоверенным: его инструкции не получают системных полномочий. До API и перед записью артефактов применяется маскирование распространённых секретов. Содержимое ответов об ошибках провайдера не выводится.

Агент не запускает приложение, не делает сетевой пентест и не подтверждает инфраструктурные права ОС, сертификацию либо юридическое соответствие. Повторная LLM-проверка использует тот же провайдер и не является независимым экспертным аудитом. Полнота, точность и длительность должны быть измерены на версиях организаторов; скрытая разметка отсутствует.

Верификатор также может запросить до двух раундов дополнительных диапазонов исходников. Ошибочные ссылки получают ограниченные исправления; если доказательства недоступны, сохраняется uncertain. Это устраняет разрыв, при котором review мог получать контекст, а verify только перечислял недостающие файлы.

Контекст verify подбирается под лимит: сама находка и её исходные доказательства сохраняются полностью; дополнительный контекст включается по бюджету. Число невключённых элементов явно отмечается, а полный каталог диапазонов позволяет запросить нужные части. Переполнение доказательств самой находки не маскируется усечением.
