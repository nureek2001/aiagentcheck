# Полный процесс работы

## Проверка и объяснения

Push или ручной запуск Product security выполняет два независимых задания:
Product tests запускает существующие тесты Helpdesk на Windows без DeepSeek/GitHub
секретов в окружении процесса; security проверяет неизменный снимок доверенным агентом.
Тестовая среда использует Python UTF-8 и временный HELPDESK_RUNTIME.
Доставка зависит от обоих заданий. Реального развёртывания пример не выполняет.

Во вкладке «Находки» показаны причина/последствия, рекомендация, исходные строки
и результат отдельной перепроверки. Нажатие на требование в таблице раскрывает
обоснование его статуса и подтверждающие фрагменты. Это пояснение результата,
а не скрытые рассуждения модели. Отчёты не переводятся через API при смене языка.

## Сравнение

Выбранный отчёт сравнивается с другим сохранённым отчётом. Сопоставление использует
требование, причину, пути, пересечение строк и текст находки. Это эвристика,
а не доказательство тождества: модель может переформулировать или объединить находки.
Категории: новые, сохранились, не обнаружены повторно. Последняя категория никогда
автоматически не называется «исправлено». При неполном отчёте показано предупреждение.
Открытые объяснения сохраняются при обновлении телеметрии.

## Бюджет

По умолчанию на отдельный аудит: 8 000 000 токенов и 250 попыток API.
Настройка локальной панели действует на новые локальные проверки и предложения.
Для Actions используются inputs max_tokens/max_requests reusable workflow.
Ограничение локальной панели не меняет настройки GitHub автоматически.

CLI: `scan --max-tokens 8000000 --max-requests 250`. Переменные окружения:
DEEPSEEK_MAX_TOKENS и DEEPSEEK_MAX_REQUESTS. Повторные сетевые запросы учитываются.
Перед отправкой резервируется консервативная оценка: UTF-8 размер сообщений,
лимит ответа и запас. После ответа резерв заменяется фактическим usage. Если
usage недоступен, оценка остаётся расходом. Резервирование защищено блокировкой
для параллельных запросов. Это ограничитель запросов, не гарантия счёта провайдера;
фактический счёт определяется DeepSeek. При исчерпании бюджета — код 2.
Метрики budget.json отделяют reported_tokens от charged_or_estimated_tokens.

## Живой прогресс GitHub

Агент пишет Check «KMG agent progress» не чаще одного обновления за 20 секунд.
Передаются только разрешённые поля: этап, число фрагментов, время, идентификатор ИБ,
usage и итоговый код. Нет исходников, текста находок или ключей. Нужен checks:write
для GITHUB_TOKEN; целевой код в этом задании не исполняется. Check имеет neutral
conclusion: решение security gate определяется exit code, не мониторингом.

Панель читает Check с точным external_id run_id:attempt. Старые события не выдаются
за актуальные: после 180 секунд без обновления показываются шаги Actions.
Ошибка мониторинга не изменяет вывод проверки. Старые версии без телеметрии
продолжают отображаться через крупные шаги Actions.

## Исправление и PR

1. Выбрать основную находку актуального отчёта и подтвердить платную генерацию патча.
2. Просмотреть diff, ограничения и предложенные тесты.
3. Подтвердить отдельное действие: push новой ветки, тесты, платный повторный аудит, PR.
4. Агент сверяет SHA-256 просмотренного патча, коммит, полный fingerprint и чистоту
   локального проекта. Изменившийся patch или base блокируют публикацию.
5. Структурированные before/after снова проверяются. Через GitHub Git Data API
   создаётся ветка security-fix/<hash>. Основная ветка и локальный проект не меняются.
   Тесты, лицензии и скрытые служебные каталоги не редактируются механизмом публикации.
6. Push вызывает Product security: тесты продукта и полный повторный аудит.
7. После CI агент создаёт PR. Если оба обязательных задания успешны, PR готов
   к рассмотрению. Иначе или при истечении ожидания — draft с явными ограничениями.
   Подготовка может занять до 35 минут, работает отдельным процессом.
8. Разработчик изучает PR и самостоятельно принимает решение о слиянии.

Статус операции хранится в pr.json. Повторная публикация уже начатой операции
блокируется, чтобы не создавать дубликаты. При сбое проверяйте сохранённую ветку
и CI перед повтором; автоматического удаления веток нет. Рекомендуемые моделью
команды не исполняются локально. Тестовая команда задаётся доверенным workflow.
В примере используется `python manage.py test portal --noinput`; для другого
продукта нужно заменить её его тестовым процессом. Наличие одного теста Helpdesk
не означает полную регрессионную проверку исправления.

Репозиторий должен разрешать GitHub доступ на contents write и pull requests write
учётной записи локального Git Credential Manager / GH_TOKEN. Токен остаётся на сервере.
Без явного подтверждения кнопки API не создаёт ветку или PR. Открытие панели бесплатно.
PR того же репозитория запускает отдельный платный анализ merge-снимка. Успешный push-аудит не заменяет обязательный gate PR.
Fork PR без секрета не выдаётся за успешно проверенный.

## Размеченные примеры

`python -m kmg_agent benchmark --output reports/benchmark-new --live`

Встроены восемь маленьких синтетических функций: проверки роли, отдельный is_staff,
срок действия токена и комментарий с prompt injection. Эталон expected не отправляется
модели. Результат benchmark.json содержит TP/FP/FN/TN, ошибки, precision, recall,
число попыток и usage. Набор не участвует в логике аудита и не подсказывает модели
расположение проблем реального Helpdesk. Он измеряет классификацию отдельных функций,
а не качество полного многоэтапного агента. Для оценки на реальных проектах нужны
более крупные независимые размеченные корпуса.


Актуализация CI: main helpdesk-demo защищён обязательным `Security merge gate`.
PR проверяет merge-снимок отдельно (с дополнительным расходом API); прежнее
правило пропуска same-repository PR отменено. Старые записи о таком пропуске
описывают прежнюю версию интеграции. Официальный target в режиме сдачи неизменен.
