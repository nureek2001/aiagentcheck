# Настройка CI/CD

## Предоставленный workflow

`.github/workflows/security-check.yml` запускается на push репозитория команды и вручную. PR запускает бесплатные тесты агента; платный анализ внешнего target на PR не дублируется. Демонстрационный workflow вызывает `reusable-security.yml`, который получает агент и тестовый проект в разные каталоги. `TARGET_REPOSITORY` выбирает target (по умолчанию официальный), `TARGET_REF` фиксирует коммит; ручной параметр `target_ref` имеет приоритет. HEAD проверенного target записывается в report.json. Новые push отменяют устаревший запуск на той же ветке.

`DEEPSEEK_API_KEY` задаётся только как GitHub Actions secret. В workflow нет continue-on-error. Возвращаемый код напрямую завершает шаг. Артефакты загружаются с `if: always()`, в том числе error.json и execution.log при неудаче. Шаг delivery-gate зависит от security и пропускается при коде 1 или 2. Это демонстрация допуска, а не фактическое развёртывание приложения.

## Блокировка слияния

Для продуктового репозитория настройте защиту ветки/ruleset с обязательным security job. Точное имя status check берётся из настоящего запуска (reusable jobs могут иметь префикс вызывающего job). Без этой настройки красный workflow сам по себе не запрещает ручное слияние. Настройте также запрет обхода правила теми ролями, для которых требуется обязательный gate. В репозитории агента демонстрационный аудит заведомо уязвимого внешнего target не следует путать с качеством кода агента: для PR здесь нужны тесты самого агента.

## Событие в тестовом репозитории

Чужой push не вызывает workflow команды. У организатора следует уточнить один из вариантов: предоставленный тестовый репозиторий с согласованным CI hook, внешний dispatch, либо проверка target из репозитория решения при сдаче. Текущий workflow выполняет последний вариант и не заявляет, что защищает ветку организатора.

Для обычного собственного продукта агент можно хранить отдельно и вызывать его из pipeline этого продукта до deploy. В таком случае target checkout должен соответствовать проверяемому event SHA, а статус безопасности — требоваться на той же ветке. Не включайте API-ключ в PR недоверенного автора и не запускайте его код с секретами.

Готовый шаблон: `docs/product-workflow.example.yml`. Шаблон уже ссылается на опубликованный репозиторий агента и закреплённый
commit SHA. При обновлении агента меняйте оба значения SHA после проверки версии. Проверяемый target берётся из `github.repository` и `github.sha`:
для push — отправленный коммит, для pull_request — merge-коммит, который GitHub проверяет для PR.
Агент закреплён по SHA; target никогда не устанавливается и не исполняется. Не добавляйте секреты
через `pull_request_target`. Fork PR без DeepSeek secret не получает положительный результат.

Reusable workflow работает с публичным агентом либо с репозиториями, к которым у вызывающего
workflow есть доступ. `GITHUB_TOKEN` не даёт доступ ко всем приватным репозиториям пользователя.

## Настройка команды

1. Secret `DEEPSEEK_API_KEY` — ключ DeepSeek, только в Actions Secrets.
2. Variable `TARGET_REF` — зафиксированный SHA официального target для воспроизводимой демонстрации.
3. Variable `DEEPSEEK_MODEL` — используемая модель.
4. После push откройте Actions → Security assessment. В Summary отображаются код, число находок и
   статусы требований. В Artifacts сохраняются dashboard.html, JSON, Markdown, метрики и диагностика.
5. Если ошибка возникла до установки агента, сохраняется error.json, но HTML может отсутствовать.
   Принудительная отмена runner/истечение общего job timeout также могут помешать загрузке artifact;
   отсутствие artifact никогда не считается успехом.

Проверка DeepSeek ограничена 25 минутами, job — 30 минутами. В CI кэш карты контекста не используется.
GitHub Actions не размещает автоматически публичный сайт. Панель открывается локально и читает
GitHub, а автономная версия прикладывается к результатам. См. `DASHBOARD.md`.

## Проверка перед защитой

1. Выполнить push и убедиться, что workflow запустился автоматически.
2. Проверить SHA target в отчёте и выбранный TARGET_REF.
3. На разрешённых версиях показать коды 0 и 1; на недоступном API — 2.
4. Проверить, что deploy-преемник не выполняется при 1/2.
5. Убедиться, что Markdown, JSON и лог доступны после неуспешного анализа.
6. Сохранить настоящий лог запуска, а не лог unit-тестов.
