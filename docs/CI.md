# Настройка CI/CD

## Предоставленный workflow

`.github/workflows/security-check.yml` запускается на push репозитория команды и вручную. PR репозитория агента запускает бесплатные тесты агента; это отличается от PR продукта, где проверяется merge-снимок. Демонстрационный workflow вызывает `reusable-security.yml`, который получает агент и тестовый проект в разные каталоги. `TARGET_REPOSITORY` выбирает target (по умолчанию официальный), `TARGET_REF` фиксирует коммит; ручной параметр `target_ref` имеет приоритет. HEAD проверенного target записывается в report.json. Новые push отменяют устаревший запуск на той же ветке.

`DEEPSEEK_API_KEY` задаётся только как GitHub Actions secret. В workflow нет continue-on-error. Возвращаемый код напрямую завершает шаг. Артефакты загружаются с `if: always()`, в том числе error.json и execution.log при неудаче. Шаг delivery-gate зависит от security и пропускается при коде 1 или 2. Это демонстрация допуска, а не фактическое развёртывание приложения.

## Блокировка слияния

В helpdesk-demo настроена защита main с обязательным Security merge gate (см. актуализацию ниже). Для другого продуктового репозитория настройте аналогичное правило. Точное имя status check берётся из настоящего запуска (reusable jobs могут иметь префикс вызывающего job). Без этой настройки красный workflow сам по себе не запрещает ручное слияние. Настройте также запрет обхода правила теми ролями, для которых требуется обязательный gate. В репозитории агента демонстрационный аудит заведомо уязвимого внешнего target не следует путать с качеством кода агента: для PR здесь нужны тесты самого агента.

## Событие в тестовом репозитории

Чужой push не вызывает workflow команды. У организатора следует уточнить один из вариантов: предоставленный тестовый репозиторий с согласованным CI hook, внешний dispatch, либо проверка target из репозитория решения при сдаче. Текущий workflow выполняет последний вариант и не заявляет, что защищает ветку организатора.

Для обычного собственного продукта агент можно хранить отдельно и вызывать его из pipeline этого продукта до deploy. В таком случае target checkout должен соответствовать проверяемому event SHA, а статус безопасности — требоваться на той же ветке. Не включайте API-ключ в PR недоверенного автора и не запускайте его код с секретами.

Готовый шаблон: `docs/product-workflow.example.yml`. Шаблон уже ссылается на опубликованный репозиторий агента и закреплённый
commit SHA. При обновлении агента меняйте оба значения SHA после проверки версии. Проверяемый target берётся из `github.repository` и `github.sha`:
для push — отправленный коммит, для pull_request — merge-коммит, который GitHub проверяет для PR.
Агент закреплён по SHA; target никогда не устанавливается и не исполняется. Не добавляйте секреты
через `pull_request_target`. Fork PR без DeepSeek secret не получает положительный результат.

Reusable workflow работает с публичным агентом либо с репозиториями, к которым у вызывающего
workflow есть доступ. `GITHUB_TOKEN` не даёт доступ ко всем приватным репозиториям пользователя.

## Настройка команды

1. Secret `DEEPSEEK_API_KEY` — ключ DeepSeek, только в Actions Secrets.
2. Variable `TARGET_REF` — зафиксированный SHA официального target для воспроизводимой демонстрации.
3. Variable `DEEPSEEK_MODEL` — используемая модель.
4. После push откройте Actions → Security assessment. В Summary отображаются код, число находок и
   статусы требований. В Artifacts сохраняются dashboard.html, JSON, Markdown, метрики и диагностика.
5. Если ошибка возникла до установки агента, сохраняется error.json, но HTML может отсутствовать.
   Принудительная отмена runner/истечение общего job timeout также могут помешать загрузке artifact;
   отсутствие artifact никогда не считается успехом.

Проверка DeepSeek ограничена 25 минутами, job — 30 минутами. В CI кэш карты контекста не используется.
GitHub Actions не размещает автоматически публичный сайт. Панель открывается локально и читает
GitHub, а автономная версия прикладывается к результатам. См. `DASHBOARD.md`.

## Проверка перед защитой

1. Выполнить push и убедиться, что workflow запустился автоматически.
2. Проверить SHA target в отчёте и выбранный TARGET_REF.
3. На разрешённых версиях показать коды 0 и 1; на недоступном API — 2.
4. Проверить, что deploy-преемник не выполняется при 1/2.
5. Убедиться, что Markdown, JSON и лог доступны после неуспешного анализа.
6. Сохранить настоящий лог запуска, а не лог unit-тестов.


### Восстановление неопределённых результатов

После inconclusive или отклонения всех кандидатов агент выполняет до двух
дополнительных разборов этого требования в текущем запуске. Он передаёт замечания
верификатора, исходный вывод и ранее полученные исходники; модель может запросить
недостающий контекст. Отсутствие подтверждённых нарушений само по себе не означает pass.

Каждый разбор допускает до четырёх запросов дополнительных исходников и две попытки
исправить некорректные ссылки или противоречивый ответ. Диапазоны проверяются по
неизменному снимку: агент не обрезает ошибочные номера строк до размера файла.
Ошибка ответа для одного требования сохраняется как inconclusive, остальные требования
продолжают проверяться. Ошибки провайдера и общий лимит времени по-прежнему останавливают
запуск. Дополнительные запросы расходуют API-токены и укладываются в общий deadline.

Код 2 остаётся обязательным при неустранимой неопределённости или неполном покрытии.
Гарантировать двоичный вывод при любой ошибке API, недоступной конфигурации ОС или
недостатке доказательств невозможно. Статус pass не выставляется ради зелёного CI.

Историческая проверка этого этапа: 60 локальных тестов, включая восстановление диапазонов,
повторный разбор с получением контекста, продолжение остальных требований после
исчерпания восстановления и сохранение кода 2 при неопределённости. Эти тесты используют
фиктивный транспорт; они не доказывают окончательное устранение ИБ-05 на DeepSeek.


## Действующая защита helpdesk-demo

Main требует статус `Security merge gate` от приложения GitHub Actions (app_id=15368), strict=true, enforce_admins=true.
Этот job выполняется с always(), зависит от security и tests и успешен только
при result=success у обоих. Failure, cancelled, skipped не допускают delivery.
PR merge-снимок проверяется отдельно от push: это дополнительный платный анализ.
Старый workflow с пропуском same-repository PR больше не используется на main.
Ветки со старым workflow, где нового gate нет, не имеют обязательного статуса
и блокируются. Перед merge GitHub требует актуальность относительно main.

Настройка реально проверена на PR #1: mergeable_state=blocked, draft=false,
merged=false. PR закрыт без слияния. Во время проверки CI был намеренно пропущен
через skip ci; это подтвердило, что отсутствие успешного gate не разрешает merge.
Эта проверка не являлась повторным аудитом приложения и не расходовала DeepSeek.

Оригинальный target проверяется из репозитория агента: workflow получает
AlmasNUR/KMG-Digital-Hackathon и SHA 576e58100d7ef832cef2ad3ec73fc89ab98f84b5.
В репозиторий организаторов workflow не добавляется. Официальная демонстрация
не претендует на управление защищённой веткой чужого репозитория.

Текущая локальная проверка после доработки verify: 76 тестов прошли. Добавлены получение исходников самим верификатором и подбор дополнительного контекста в пределах лимита без усечения основных доказательств. Результат официального прогона — в OFFICIAL_RUN.md.
