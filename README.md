# KMG Security Agent

ИИ-агент для проверки всего Git-репозитория по требованиям ИБ-01…ИБ-08 хакатона KMG Digital. Использует официальный DeepSeek API, формирует JSON и Markdown и возвращает код завершения для CI/CD.

## Панель и GitHub Actions

Репозиторий команды: https://github.com/nureek2001/aiagentcheck

```powershell
.\scripts\dashboard.ps1 -GitHubRepo nureek2001/aiagentcheck
# Откройте http://127.0.0.1:8765
```

Панель показывает реальные локальные отчёты, ход scan и статусы GitHub Actions. Готовые облачные
отчёты автоматически появляются в истории. Для GitHub используется существующий вход через Git
Credential Manager или `GH_TOKEN` в локальном `.env`. Открытие панели не расходует DeepSeek-токены.

Каждый CI artifact также содержит автономный `dashboard.html`. Скачайте artifact из вкладки Actions,
распакуйте и откройте HTML. Во вкладке локальной панели «Предложение исправлений» можно отдельно
заказать патч для выбранной находки. Он не применяется к проекту; тесты исправлений не запускаются.

Демонстрационный workflow запускается по push в репозиторий агента и проверяет отдельный target.
Для проверки коммита собственного приложения используйте `docs/product-workflow.example.yml`:
он вызывает reusable workflow агента с `target_ref: github.sha`. Проект организаторов не изменяется.

**Состояние поставки:** реализация и локальные автоматические тесты готовы, подключение к настоящему DeepSeek API проверено. Выполнены реальные запуски на официальном проекте; отчёты и логи находятся в `reports/run-*`. Результат `incomplete` нельзя считать прохождением проверки. GitHub Actions подключён: настоящие push запускают анализ и тесты на Windows/Linux. Точность модели по эталонной разметке отдельно не подтверждена. Offline-инвентаризация не является отчётом безопасности.

## Быстрый запуск на Windows

Требуется Python 3.11+ и Git. Для одинаковой среды с хакатоном рекомендуется установленный Python 3.14. Сам агент не запускает Django, поэтому пакеты и база тестового приложения ему не нужны.

Из PowerShell:

```powershell
cd C:\Users\AIHUB-User\Desktop\aihub\_kmgdigital
.\scripts\setup.ps1
```

Откройте **`.env` в корне проекта** и вставьте ключ:

```dotenv
DEEPSEEK_API_KEY=ваш_ключ
DEEPSEEK_MODEL=deepseek-flash
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_TIMEOUT=120
DEEPSEEK_RETRIES=2
```

`.env` уже создан локально и исключён из Git. В распространяемом архиве есть `.env.example`; setup создаст из него `.env`. Не публикуйте ключ и не вставляйте его в README, отчёт или скриншот.

```powershell
.\scripts\scan.ps1
```

При первом запуске скрипт клонирует официальный проект в `targets/KMG-Digital-Hackathon`. Последующие запуски проверяют имеющийся checkout, не обновляя его автоматически. Каждый запуск создаёт новую папку `reports/run-ДАТА-ВРЕМЯ`. Вывод показывает её расположение и exit code. Подробный прогресс — в `execution.log` внутри этой папки.

Если выполнение PowerShell-скриптов ограничено вашей политикой, используйте непосредственно команды ниже — глобально менять политику не требуется.

## Запуск вручную

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.lock -e ".[dev]"
# При необходимости: Copy-Item .env.example .env
git clone https://github.com/AlmasNUR/KMG-Digital-Hackathon.git targets/KMG-Digital-Hackathon
.venv/Scripts/python.exe -m kmg_agent scan --repo targets/KMG-Digital-Hackathon --output reports/first-run --env-file .env --timeout 1500 --workers 2
$LASTEXITCODE
```

Для уже имеющегося чистого репозитория укажите его абсолютный путь в `--repo`. Выходной каталог должен быть новым или пустым и находиться **вне проверяемого репозитория**. Это предотвращает изменение объекта проверки и смешивание старого отчёта с новым.

Воспроизводимая проверка конкретного коммита:

```powershell
git -C targets/KMG-Digital-Hackathon checkout 576e58100d7ef832cef2ad3ec73fc89ab98f84b5
.venv/Scripts/python.exe -m kmg_agent scan --repo targets/KMG-Digital-Hackathon --output reports/pinned-run --env-file .env
```

Checkout выполняется оператором до проверки. Агент только читает файлы. Грязный checkout, неизвестный бинарный формат, неподдерживаемый подмодуль или превышение лимитов не превращаются в успешный аудит.

На Linux/macOS используйте `.venv/bin/python` вместо `.venv/Scripts/python.exe`.

## Проверка без ключа

```powershell
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe -m ruff check .
.venv/Scripts/python.exe -m kmg_agent inspect --repo targets/KMG-Digital-Hackathon --output reports/inventory
```

`inspect` читает все отслеживаемые файлы, извлекает DOCX и Python AST, создаёт инвентаризацию. Код 0 этой команды означает только успешную инвентаризацию. **В CI для допуска к развёртыванию используется исключительно `scan`.**

## Результаты `scan`

| Код | Значение | Действие CI |
|---|---|---|
| 0 | Все проверки завершены, нарушений ИБ-01…08 нет | Разрешить дальнейший шаг |
| 1 | Проверки завершены, есть подтверждённые нарушения ИБ | Заблокировать |
| 2 | Проверка не выполнена полностью или произошла ошибка | Заблокировать; не считать отсутствием нарушений |

Дополнительные замечания спецификации находятся отдельно и сами по себе не вызывают код 1. При незавершённом анализе код 2 имеет приоритет, даже если отдельные нарушения уже подтверждены.

Артефакты успешного выполнения анализа, включая результат `fail`:

- `report.json` — основной отчёт, восемь статусов, находки, доказательства, покрытие, SHA и метрики;
- `report.md` — читаемая версия того же JSON;
- `inventory.json` — исходный снимок: пути, размеры, хеши, исключения и AST-факты;
- `metrics.json` — длительность, модель и токены, полученные из API;
- `execution.log` — этапы, код завершения, число нарушений и нарушенные требования.

При ошибке также создаётся `error.json`. При недоступности API отчёт аудита **не создаётся**, согласно п. 4.7.3 ТЗ; сохраняются диагностика и инвентаризация. При общем таймауте сохраняется частичный отчёт из контрольной точки, если анализ уже начался, согласно п. 4.7.2. Конфликт формулировки п. 4.3.4 с п. 4.7.3 описан в `docs/DECISIONS.md`.

По умолчанию лимит — 1500 секунд. Максимальный разрешённый лимит агента — 1740 секунд, чтобы оставить резерв до 30 минут. Родительский процесс принудительно завершает зависший worker. Скорость и полноту при реальном API нужно измерить, а не считать гарантированными.

Успешные промежуточные наблюдения сохраняются в `reports/.context-cache` на сутки. Повторно используются только фрагменты с идентичным текстом, моделью, инструкциями и схемой; итоговые проверки требований выполняются заново. Кэш не является готовым отчётом и не превращает проверку в анализ git diff. Для полностью нового API-прогона добавьте `--no-cache`. Если модель обрезала ответ по лимиту вывода, крупный фрагмент делится без пропуска текста. Некорректные JSON-ответы и ссылки на строки проходят ограниченный цикл исправления; непроверенные данные не принимаются.

## DeepSeek

Только `https://api.deepseek.com`, без перенаправлений на другие хосты. Ключ передаётся в заголовке Authorization. Модель задаётся переменной `DEEPSEEK_MODEL`; проверьте модель, разрешённую организаторами и доступную вашему ключу. Используются Chat Completions, JSON mode, отключённый thinking и temperature=0. Структура ответа дополнительно проверяется JSON Schema.

Сбор контекста и решения выполняются локально; очищенные фрагменты кода передаются DeepSeek. Маскирование секретов эвристическое и не является гарантией удаления любых произвольных секретов. Передавайте только разрешённые организаторами исходники и синтетические данные.

Официальные источники:

- https://api-docs.deepseek.com/api/create-chat-completion/
- https://api-docs.deepseek.com/api/list-models/
- https://api-docs.deepseek.com/quick_start/rate_limit/

## GitHub Actions

1. Создайте GitHub-репозиторий команды и отправьте исходники агента без `.env`, `.venv`, `targets` и `reports`.
2. В Settings → Secrets and variables → Actions добавьте secret **`DEEPSEEK_API_KEY`**.
3. При необходимости добавьте variables `DEEPSEEK_MODEL` и `TARGET_REF` (SHA либо ref тестового проекта).
4. Запустите workflow **Security assessment**. Он также запускается при push/PR в репозиторий агента.
5. В правилах защищённой ветки сделайте проверку **Required security gate** обязательной. Сам файл YAML не настраивает защиту ветки.
6. Реальный deploy должен зависеть от `security` через `needs`. В поставке есть демонстрационный зависимый шаг, но нет выдуманного развёртывания.

Workflow получает официальный тестовый проект отдельным checkout. Он проверяет актуальный выбранный ref и записывает его SHA в отчёт. Push в чужой репозиторий организаторов не запускает workflow команды автоматически: для этого необходима согласованная с организаторами интеграция события/dispatch. См. `docs/CI.md`.

API-ключ недоступен workflow из внешних fork PR; в таком случае проверка корректно завершается с кодом 2. Не используйте `pull_request_target` для исполнения неподтверждённого кода с ключом.

## Границы применимости

Это статический анализ с LLM, а не доказательство отсутствия уязвимостей. Проверяются поддерживаемые отслеживаемые текстовые файлы и DOCX. Изображения, шрифты и бинарные локализации учитываются в инвентаризации без анализа содержимого; потенциальные ключи/БД исключаются из передачи, но их наличие видно модели. Неизвестные бинарные документы приводят к ошибке, а не тихому пропуску. Python AST помогает разобраться в связях, но не заменяет полноценный межпроцедурный анализ.

Результаты могут различаться при повторных вызовах или обновлении модели. Ограниченные циклы запроса контекста и перепроверка снижают риск ошибочных находок, но не гарантируют точность. Неподтверждённые находки переводят требование в `inconclusive`, а не автоматически в `pass`.
